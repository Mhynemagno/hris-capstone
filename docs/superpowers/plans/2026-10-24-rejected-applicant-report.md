# Rejected Applicant Access and Formal Report Header Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Block rejected applicants from logging in while producing official-style PDFs with centered, attributable, numbered headers.

**Architecture:** Add a database trigger so a failed outcome deactivates the applicant profile, which is already wired to Supabase Auth bans, revoked sessions, login denial, and RLS; HR reactivation remains blocked for six months after that decision. Pass the trusted HR role label from the protected report route to the small server-side PDF builder.

**Tech Stack:** Next.js 16 route handlers, TypeScript, Vitest, Supabase/PostgreSQL migrations and pgTAP.

**Spec:** `docs/superpowers/specs/2026-10-24-rejected-applicant-report-design.md`

## Global Constraints

- Preserve existing applicant, decision, audit, and notification history.
- Use the existing profile deactivation/Auth-ban path; do not add a browser-only authorization check.
- Keep PDF generation server-side, without third-party dependencies.
- Keep CSV and report-table behavior unchanged.

## Review Focus

- A non-failed stage result must leave the applicant account active; test this in the recruitment pgTAP suite.
- A failed stage must deactivate exactly its applicant, not the HR actor; test the profile row after the RPC.
- Existing login protections must receive the state via the Auth-ban trigger; test both the profile and `auth.users.banned_until`.
- A direct PDF request must use the authenticated profile’s name rather than a caller-controlled query value; test route-to-builder arguments.
- Every generated PDF page must preserve a centered header and `Page N of M`; test a multi-page output.
